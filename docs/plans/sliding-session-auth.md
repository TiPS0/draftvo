# Sliding Session Auth

> **Generated by `/agent-plan`**
> **Date:** 2026-08-21
> **Type:** enhance_feature

## 1. Summary

Implement a 1-day sliding session logic by reducing the JWT hard-expiration to 24 hours, and automatically issuing a refreshed token in `proxy.ts` if the current valid token is older than 12 hours.

## 2. Affected Screens & Components

List every file that will likely need to be created or modified:

- **[MODIFY]** `frontend/src/lib/auth.ts` — Reduce `TOKEN_TTL_SECONDS` to 1 day (24 hours).
- **[MODIFY]** `frontend/src/proxy.ts` — Add logic to check `payload.iat`. If older than 12 hours, generate a new JWT and set it in the response cookies.

## 3. User Flow (Step-by-Step)

1. User logs in, receives a JWT valid for 24 hours.
2. User returns to the app within 12 hours: App authenticates normally, no refresh occurs.
3. User returns to the app between 12-24 hours: App authenticates, detects token is older than 12 hours, transparently generates a new 24-hour JWT, and sets it in the response cookie.
4. User returns after 24 hours: Token is expired. App redirects to `/login`.

## 4. Technical Requirements

### Data & State
- Token TTL reduced to `60 * 60 * 24` (1 day).
- Refresh threshold: `(Math.floor(Date.now() / 1000) - payload.iat) > 60 * 60 * 12` (12 hours).

### Navigation
- Middleware (`proxy.ts`) handles the refresh logic transparently without navigating away from the requested route.

### API / Mock Data
- Use the existing `signJwt` function in `proxy.ts` to generate the new token. Pass `{ sub: payload.sub, name: payload.name, role: payload.role }` from the verified payload to `signJwt`.

## 5. Design & UX Notes

- This change is entirely transparent to the user. No UI changes are needed.

## 6. Hard Constraints (DO NOT CHANGE)

List everything that must remain untouched:

- Do NOT implement a database check for sessions. Keep it stateless.
- Do NOT refresh the token on every request (must respect the 12-hour threshold).
- Do NOT remove the existing `Cache-Control` logic in `proxy.ts`.
