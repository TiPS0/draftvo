## 1. Summary

Implement a robust authentication architecture for a self-hosted environment based on the `authentication-and-privacy-architecture.md` grill. This includes replacing basic JSON login with HTTP-only cookies for session security, introducing role-based access (Admin vs. Member), and restricting registration so that the first user becomes the Admin and all subsequent users require an invite token.

## 2. Affected Screens & Components

- **[MODIFY]** `backend/main.go` — 
  - Add `Role` field to the `User` struct.
  - Update `/auth/register` to check for an empty DB (first user = Admin) and require a valid invite token for all others.
  - Update `/auth/login` to return an HTTP-only cookie containing a secure session token (JWT) instead of just JSON.
  - Add middleware to verify HTTP-only cookies on protected routes.
  - Add an endpoint `POST /api/invites` (Admin only) to generate invite tokens.
- **[NEW]** `backend/invites.json` — A simple JSON file store to persist active invite tokens.
- **[MODIFY]** `frontend/src/app/(auth)/login/page.tsx` — Update the API call to expect the new cookie-based login flow (ensure credentials are included in fetch).
- **[MODIFY]** `frontend/src/app/(auth)/register/page.tsx` — Add an "Invite Token" input field. The frontend should handle errors gracefully if a token is required but missing.
- **[NEW]** `frontend/src/app/(main)/settings/users/page.tsx` — A new page for Admins to manage users and generate invite tokens.

## 3. User Flow (Step-by-Step)

1. A user navigates to the Registration page. If they are the first user ever on this server, they sign up normally and become the `Admin`.
2. As an Admin, they navigate to Settings > Users and click "Generate Invite Link/Token".
3. The Admin shares the token securely with a team member.
4. The team member navigates to the Registration page, enters their details AND the Invite Token.
5. They are successfully registered as a `Member`.
6. Users login via the Login page and receive an HTTP-only cookie, securing their session against XSS attacks.

## 4. Technical Requirements

### Data & State
- Add `Role` field to `User` (string, either "Admin" or "Member").
- Create an `Invite` struct (ID, Token, CreatedAt, CreatedBy, Used) and store in `invites.json`.

### Navigation
- Next.js should check for the presence of the HTTP-only cookie (or an `isLoggedIn` endpoint). If missing on protected routes, redirect to `/login`.

### API / Mock Data
- `POST /auth/register`: Expects `{ name, email, password, inviteToken }`.
- `POST /auth/login`: Sets `Set-Cookie: auth_token=...; HttpOnly; Path=/; Secure; SameSite=Lax`.
- `POST /api/invites`: (Admin only) Generates and returns a new invite token.
- `GET /api/auth/me`: Returns current logged-in user and role based on cookie verification.

## 6. Hard Constraints (DO NOT CHANGE)

- The backend MUST remain a single Go executable using JSON files for storage (`users.json`, `invites.json`). Do not migrate to a complex database (like Postgres) at this time.
- Do NOT use third-party auth services (e.g., Auth0, Clerk, Firebase) since this is designed to be a fully self-hosted, offline-capable tool.
- Follow the `kebab-case.md` filename rule for this plan.
